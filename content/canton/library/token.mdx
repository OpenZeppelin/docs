title: Token (CIP-0112)
---

The token packages implement a registry on the Token Standard V2 interfaces from [CIP-0112](https://github.com/canton-foundation/cips): holdings, transfer instructions, allocations with batch and iterated settlement, mint offers, and an event log. Its closest Solidity analogue is a partial `ERC20`.

Use the ready-to-use templates, or own your templates and reuse only the choice bodies.

<Callout type="warn">
  Pre-release and unaudited. The packages have no release yet. Source:

## Packages

| Package | Modules | Contents |
| --- | --- | --- |
| `openzeppelin-token-cip112-types-v1` | `OpenZeppelin.Token.Cip112.TypesV1` | The records that the templates store: `RegistryConfig`, `TransferInstructionState`, and `AllocationState`. |
| `openzeppelin-token-cip112-utils` | `OpenZeppelin.Token.Cip112.Utils.Holding`, `.Transfer`, `.Allocation`, `.Registry` | The choice bodies of a registry as functions over your own templates. |
| `openzeppelin-token-cip112-v1` | `OpenZeppelin.Token.Cip112.V1.Holding`, `.Transfer`, `.Allocation`, `.Registry`, `.Base` | Ready-to-use templates over the utils. |

The packages depend on the Splice Token Standard V2 interface DARs. The DARs in `dars/vendor/` are byte-identical copies of the Splice `0.8.3` release, so their package IDs are the ones that Splice deployments already vet.

## Templates

`openzeppelin-token-cip112-v1` implements the matching `Splice.Api.Token.*V2` interfaces. Each choice body is a function of the utils package.

| Module | Template | Purpose |
| --- | --- | --- |
| `.Holding` | `TokenHolding` | An asset holding, maintained jointly by the instrument admin and the account parties, with optional locks and an owner-unlock choice. |
| `.Transfer` | `TokenTransferInstruction` | The transfer-instruction lifecycle: accept, reject, withdraw, and expire. |
| `.Allocation` | `TokenAllocation` | Allocations backed by locked holdings, with exact-cover batch settlement and iterated settlement. |
| `.Registry` | `TokenRules` | The registry rules: transfer, allocation, and settlement factories, mint offers, and expiry. |
| `.Base` | `TokenEventLog` | The event log for holding changes. |

## Lifecycle

- **Transfer.** A transfer completes in one step when the receiver's account parties authorize the same transaction. Otherwise the receiver accepts a pending instruction before `executeBefore`. The sender can withdraw a pending instruction at any time. After `executeBefore`, the admin can also return the funds with `TokenTransferInstruction_Expire`.
- **Mint.** The admin offers supply with `TokenRules_OfferMint`: a pending instruction from the CIP-0112 mint account (`cip-112/mint`) that locks nothing. The receiver accepts or rejects it. A mint is always two-step.
- **Burn.** A holder transfers to the CIP-0112 burn account (`cip-112/burn`). The admin accepts or rejects the burn request; the holder and the admin acting together burn in one step.
- **Settlement.** `SettlementFactory_SettleBatch` settles allocations together and checks exact cover: every leg needs a sending and a receiving allocation of the same amount.
- **Iterated settlement.** An allocation with `nextIterationFunding` lets the executors add legs in each iteration, bounded by the locked reserve plus incoming credits, and reserve funding for a successor allocation.
- **Canonical rules.** The application selects and discloses the one `TokenRules` contract for its instrument.

## Using the Utils With Your Own Templates

The utils package defines no templates, interfaces, or serializable types, so SCU ignores it and your contracts do not reference it. Build a `HoldingOps` record inside your choice bodies, and call the `*Impl` functions, for example `transferFactoryImpl`, `allocationFactoryImpl`, `settleBatchImpl`, and `offerMintImpl`.

The functions trust only what your templates supply:

- **Consume holdings safely.** Use `consumeByArchive @YourHolding`, or a spend choice reached through `fetchFromInterface @YourHolding`. Never archive a caller-supplied contract ID through the interface.
- **Pin allocations.** Pass `pinAllocationTo @YourAllocation` to `settleBatchImpl` and `expireAllocationsImpl`.
- **Keep exact cover.** Settle through `settleBatchImpl`. No other choice may exercise `Allocation_Settle` with the admin's authority.
- **Guard mint offers.** Only `offerMintImpl`, from a choice that the admin alone controls, may create an instruction from the mint account.

[`examples/token/token-cip112-custom`](https://github.com/OpenZeppelin/canton-contracts/tree/main/examples/token/token-cip112-custom) owns its templates and adds roles, an auditor, a compliance freeze, a pause switch, a transfer fee, and an executor allowlist.

## Security Considerations

- **Admin co-signing.** The exact-cover check runs only inside `SettlementFactory_SettleBatch`. A direct `Allocation_Settle` by the admin and the executors bypasses it and can create or destroy value. Operate the admin so that it signs settles only through the settlement factory.
- **Iterated settlement.** The executors control the reserve in each iteration. Enable it only with executors that you trust with the reserved amount, and bound it with a settlement deadline.
- **Supply-change allocations.** A mint-account or burn-account allocation commits the admin to that supply change until the settlement deadline or a withdrawal.
- **Lock parameters.** Size `lockGrace` to the reaction time of the admin's cleanup automation, and `maxTTL` to the longest workflow that the registry accepts.
- **Owner recovery.** `TokenHolding_OwnerUnlock` needs every account party, so an unresponsive provider blocks recovery.

## V1 Compatibility

The V2 interfaces share only `splice-api-token-metadata-v1` with V1, so V1 tooling cannot see this token. To support V1, add the V1 interface instances to the same templates. The vendored `splice-token-standard-utils` DAR has the `...V1...DefaultImplUsingV2` helpers for this.

## Build and Consume

From the root of `canton-contracts`:

```bash
DAML_PACKAGE=packages/token/token-cip112-types-v1 dpm build
DAML_PACKAGE=packages/token/token-cip112-utils dpm build
DAML_PACKAGE=packages/token/token-cip112-v1 dpm build
```

In your project, add the token DARs and the vendored interface DARs as `data-dependencies`. A project that owns its templates leaves out `openzeppelin-token-cip112-v1`.

```yaml
data-dependencies:
  - ../canton-contracts/packages/token/token-cip112-types-v1/.daml/dist/openzeppelin-token-cip112-types-v1-0.1.0.dar
  - ../canton-contracts/packages/token/token-cip112-utils/.daml/dist/openzeppelin-token-cip112-utils-0.1.0.dar
  - ../canton-contracts/packages/token/token-cip112-v1/.daml/dist/openzeppelin-token-cip112-v1-0.1.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-metadata-v1-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-holding-v2-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-transfer-events-v2-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-allocation-v2-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-transfer-instruction-v2-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-api-token-allocation-instruction-v2-1.0.0.dar
  - ../canton-contracts/dars/vendor/splice-token-standard-utils-2.0.0.dar
build-options:
  - --target=2.1
```

```daml
import OpenZeppelin.Token.Cip112.V1.Registry
```

## Testing

- **Unit tests.** `DAML_PACKAGE=test/token-cip112-v1-test dpm test` runs the Daml Script suites on an in-memory ledger. CI requires full template and choice coverage.
- **Sandbox gate.** `scripts/check-sandbox.sh` runs mint offers, transfers, queries, and burns against a static-time Canton sandbox over the Ledger API. It needs `dpm`, Java 21 or newer, `lsof`, and a free Ledger API port (`6865` by default, or set `OZ_LEDGER_PORT`). CI runs this gate on every pull request.
- **Example.** [`examples/token/token-cip112-trading-test`](https://github.com/OpenZeppelin/canton-contracts/tree/main/examples/token/token-cip112-trading-test) launches a registry and drives it through the standard interfaces: funded allocations, DvP batch settlement, and the iterated-settlement deposit flow.
