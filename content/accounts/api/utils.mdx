Crosschain signature verification helper for ERC-7964 compliant signatures.

[ERC-7964](https://eips.ethereum.org/EIPS/eip-7964) enables a single signature to
be valid across multiple chains by omitting the `chainId` from the EIP-712 domain
and encoding chain-specific operations as an array of struct hashes. This helper
provides functions to parse and verify such crosschain signatures.

The signature encoding includes metadata that allows contracts to:
* Detect crosschain signatures via a magic prefix
* Identify which operation in the array corresponds to the current chain
* Reconstruct the full EIP-712 hash for verification
* Validate the signature using standard ECDSA or ERC-1271

Verifies an ERC-7964 crosschain signature for a given `signer`, `hash` and `erc7964Signature`.
Uses the provided `structHash` function to compute the main struct hash from the array of
chain-specific struct hashes.

This function:

1. Parses the ERC-7964 signature encoding to extract metadata
2. Verifies that the provided `hash` matches the struct at `structIndex` in the array
3. Queries the application contract for EIP-712 domain information
4. Reconstructs the full typed hash using the domain and array of struct hashes
5. Validates the signature against the reconstructed hash

<Callout>
Unlike ECDSA signatures, contract signatures are revocable, and the outcome of this function can thus
change through time. It could return true at block N and false at block N+1 (or the opposite).
</Callout>

<Callout type="warn">
Make sure the `structHash` function pointer manages memory correctly. Otherwise,
this function may behave unexpectedly.
</Callout>

Utility functions for the [ERC-8043](https://eip.tools/eip/8043) init mode.

Init mode allows an ERC-4337 user operation to install one or more ERC-7579 modules
atomically alongside its regular execution. It is triggered by prefixing the user
operation's `initCode` with [`ERC8043Utils.INIT_MODE_MAGIC_VALUE`](#ERC8043Utils-INIT_MODE_MAGIC_VALUE-bytes4); the remaining bytes carry an
ABI-encoded installation payload followed by an EIP-712 signature over the
`InitModules` struct authorizing the installation.

<div className="px-4">

Attempts to decode an ERC-8043 init mode payload from `data`.

`data` must be the user operation's `initCode` with the [`ERC8043Utils.INIT_MODE_MAGIC_VALUE`](#ERC8043Utils-INIT_MODE_MAGIC_VALUE-bytes4)
4-byte prefix already stripped. Callers are expected to detect init mode
themselves — typically by comparing `initCode[:4]` against [`ERC8043Utils.INIT_MODE_MAGIC_VALUE`](#ERC8043Utils-INIT_MODE_MAGIC_VALUE-bytes4)
— before invoking this function.

`valid` is `true` when the payload decodes into four consistent, non-empty
arrays: `moduleTypeIds.length == modules.length == initDatas.length > 0`. When
`valid` is `false` the returned slices should not be relied on; individual
fields whose sub-decoder failed are returned as empty slices, but fields that
decoded before the inconsistency was detected may be populated. Callers that
want strict init-mode semantics should reject the user operation in that case.

The decoding never reverts on malformed input: length and offset checks are
performed inline before any calldata slice is materialized.

</div>
</div>

Utility contract that bridges multisig accounts with Fully Homomorphic Encryption (FHE).

When a multisig account interacts with a confidential token (e.g. ERC-7984), one signer
typically constructs the encrypted input off-chain and packages it with an input proof. The
remaining signers cannot independently inspect or reconstruct the encrypted value, they must
trust the submitting signer's off-chain preparation.

Additionally, Zama's FHE Access Control List (ACL) only supports EOA addresses as decryption
recipients; it does not natively support smart-contract multisigs. This means signers that are
not EOAs cannot receive decryption rights that their signers can act on.

### Solution

This contract provides two capabilities:

1. **Encrypted value creation**: Any caller can submit an externally-encrypted FHE value along
   with its input proof. The contract verifies the proof and stores ACL permissions so that both
   this coordinator and the target account can subsequently use or re-share the handle.
   The resulting handle is returned for use in downstream calls (e.g. `confidentialTransferFrom`).

2. **Handle allowance granting**: Any authorized signer (or the account itself) can grant
   ACL permission over an existing encrypted handle to an arbitrary EOA or contract address.
   This lets signers individually expose a confidential value to their own EOA for decryption,
   without the account contract having to approve anything.

### Setup

This is an abstract contract. Concrete deployments must also inherit an fhEVM coprocessor
configuration. For Zama's fhEVM this is done by inheriting `ZamaEthereumConfig` from the
[FHEVM Solidity package](https://github.com/zama-ai/fhevm/tree/main/library-solidity) alongside
this contract:

```solidity
contract MyMultisigCoordinator is MultisigCoordinator, ZamaEthereumConfig {}
```

A single deployment can serve multiple accounts: each account is identified by its address.
Before using [`MultisigCoordinator.allowHandle`](#MultisigCoordinator-allowHandle-address-bytes-bytes-bytes32-address-), an account must register its associated
[`ERC7579Multisig`](/accounts/api/modules#ERC7579Multisig) module by calling [`MultisigCoordinator.setERC7579Multisig`](#MultisigCoordinator-setERC7579Multisig-address-) from the account itself (e.g. via a
UserOperation's `execute` call).

### Signature scheme

When an explicit signer and signature are supplied, the signed digest is an EIP-712 typed
data hash anchored to the `account`'s own domain separator. The domain is retrieved at
call-time via `IERC5267-eip712Domain`, so no additional configuration of this coordinator
is needed.

<Callout>
[`MultisigCoordinator.fromExternal`](#MultisigCoordinator-fromExternal-address-bytes32-bytes-enum-FheType-) does not require prior registration; it grants ACL permissions to
any address provided as `account`, regardless of whether a multisig has been configured.
</Callout>

Verifies an externally-encrypted handle input proof and registers ACL permissions.

The proof is validated by `FHE-fromExternal`, after which both this coordinator (`address(this)`)
and the target `account` are permanently allowed to use the resulting handle.

The returned handle can be cast to the appropriate type using with `ebool.wrap(externalHandle)`
for `ebool`, `eaddress.wrap(externalHandle)` for `eaddress`, `euint8.wrap(externalHandle)` for
`euint8` and so on.

<Callout>
Anyone can call this function for any `account` address. ACL permissions are additive
and the caller has no ability to revoke them, so there is no griefing risk.
</Callout>

Grants a permanent ACL permission over an encrypted `handle` to address `to`, verified
against the account's registered [`ERC7579Multisig`](/accounts/api/modules#ERC7579Multisig).

See [`MultisigCoordinator._validateAccess`](#MultisigCoordinator-_validateAccess-address-bytes-bytes-bytes32-) for the full authorization rules.

Once authorization is confirmed, the `handle` is permanently allowed to `to` via the FHE
ACL. This enables `to` (typically an EOA) to request off-chain decryption of the value.

<Callout type="warn">
This grant is permanent and irrevocable. If `to` is later removed from the
multisig, they will still be able to decrypt any handle they were previously allowed. To
remove a former signer's access, re-encrypt the sensitive values using fresh FHE inputs
and grant access only to current signers.
</Callout>

Requirements:

* `account` must have a multisig registered via [`MultisigCoordinator.setERC7579Multisig`](#MultisigCoordinator-setERC7579Multisig-address-) and installed as a validator.
* `account` must implement `IERC5267`.
* The EIP-712 domain returned by `account` must not set the extensions flag (bit `0x20` of `fields`),

<div className="px-4">

Validates that `signer` is authorized to act for `account` over the given `hash`.

First confirms that the registered multisig module is actually installed as a validator on
the account (via `IERC7579ModuleConfig-isModuleInstalled`), then applies the following
authorization rules:

- If `signer` is empty: `msg.sender` must be `account` itself or a registered signer EOA.
- If `signer` is exactly 20 bytes: treated as an EOA; must be a registered signer and
  `signature` must be a valid EIP-712 signature over `hash`.
- If `signer` is more than 20 bytes: treated as an ERC-7913 signer (`verifier || key`);
  must be a registered signer and `signature` is forwarded to the verifier via
  `IERC7913SignatureVerifier-verify`.

<Callout>
Existing FHE ACL permissions (`FHE.isAllowed`) are intentionally not checked here.
Authorization is strictly tied to the account's multisig membership. Callers that already
hold ACL access to a handle and wish to extend it to another address can do so directly via
the FHE ACL (e.g. `FHE.allow`) without involving this coordinator.
</Callout>

Requirements:

* `account` must have a multisig registered via [`MultisigCoordinator.setERC7579Multisig`](#MultisigCoordinator-setERC7579Multisig-address-) and installed as a validator.

</div>
