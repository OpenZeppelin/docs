---

This page provides the full API for the Multisig modules.

<Callout type='info'>
  For an overview of the modules, read the [Multisig guide](../multisig).
</Callout>

The page covers the following modules:

- [Signer](#Signer): the registry of who may approve and how many approvals are required, generic over the signer identity type.
- [ProposalManager](#ProposalManager): the lifecycle of transfer proposals, independent of the token kind.
- [ShieldedTreasury](#ShieldedTreasury): holds one shielded coin per token color on the ledger and sends from it.
- [ShieldedTreasuryStateless](#ShieldedTreasuryStateless): receives and sends shielded coins without keeping any ledger state.
- [UnshieldedTreasury](#UnshieldedTreasury): holds unshielded tokens with a tracked per-color balance.
- [ForwarderPrivate](#ForwarderPrivate): forwards shielded deposits to a parent stored as a commitment.
- [ForwarderShielded](#ForwarderShielded): forwards shielded deposits to a public parent in the same transaction.
- [ForwarderUnshielded](#ForwarderUnshielded): forwards unshielded deposits to a public parent in the same transaction.

#### assertThresholdMet [toc] [#Signer-assertThresholdMet]
#### [!toc] [#Signer-assertThresholdMet]
<APIItemCompact
  circuitSig='assertThresholdMet(approvalCount: Uint<8>) → []'
  kind="circuit"
  complexity="k=9, rows=54"
  modulePrefix="Signer"
>
  Asserts that the given approval count meets the threshold.

  `approvalCount` is supplied by the consuming contract and is
  compared against the threshold only. This circuit never consults the signer
  registry. Ensuring the count reflects distinct, currently-registered signers
  is the consuming contract's responsibility, and a contract whose approval
  accounting is not itself gated by `assertSigner` gets no protection here.

  The count is deliberately left unbounded by `_signerCount`: approvals
  collected before a signer was removed must still count toward a threshold
  the remaining signers satisfy, and bounding the count would reject those.
  See the stale-signer-set guidance in the module header.

  Requirements:

  - Ledger threshold must be set (not be zero). An unconfigured module has a
    zero threshold, so this rejects before any approval count is compared.
  - `approvalCount` must be >= threshold.
</APIItemCompact>

#### _setThreshold [toc] [#Signer-_setThreshold]
#### [!toc] [#Signer-_setThreshold]
<APIItemCompact
  circuitSig='_setThreshold(newThreshold: Uint<8>) → []'
  kind="circuit"
  complexity="k=6, rows=40"
  modulePrefix="Signer"
>
  Sets the approval threshold without checking
  against the current signer count.

  <Callout type='warn'>
    This is intended for use during contract construction
    or custom setup flows where signers may not yet be registered.

    Leaving `newThreshold` above the signer count is permitted and expected
    mid-setup, and is not self-enforcing: `assertThresholdMet` compares
    `approvalCount` against the threshold alone, so a caller supplying a matching
    count satisfies it even against an empty registry. Contracts must not gate
    operations on `assertThresholdMet` while setup is incomplete. Lower the
    threshold with `_setThreshold`; `_changeThreshold` cannot lower one while the
    signer count is zero, because that would require a zero threshold.
  </Callout>

  Access control is NOT enforced here.
  The consuming contract must gate this behind its own
  authorization policy. Use `_changeThreshold` for
  operational threshold changes with signer count validation.

  Requirements:

  - `newThreshold` must not be zero.
</APIItemCompact>

#### _deposit [toc] [#ShieldedTreasury-_deposit]
#### [!toc] [#ShieldedTreasury-_deposit]
<APIItemCompact
  circuitSig='_deposit(coin: ShieldedCoinInfo) → []'
  kind="circuit"
  modulePrefix="ShieldedTreasury"
>
  Receives a shielded coin into the treasury.

  The coin is first claimed at the protocol level via `receiveShielded`,
  which allocates the Merkle tree index required by `insertCoin`.
  The coin is then merged with any existing coin of the same color,
  or inserted as a new entry if no coin of that color exists.

  Zero-value deposits are permitted and are not always a no-op. On a color the
  treasury does not yet hold, a zero-value coin is inserted and occupies that
  color's single slot until a later deposit merges into it; if a coin of that
  color already exists, the zero merges into it via `mergeCoinImmediate` and
  the stored value is unchanged. They may serve as signaling mechanisms when
  events are supported. They are not useful as privacy decoys, this
  treasury's holdings are public (see the module header).

  Access control is NOT enforced here.
  The consuming contract must gate this behind its own
  authorization policy.

  Requirements:

  - Deposit must not cause received total overflow.
</APIItemCompact>

#### _send [toc] [#ShieldedTreasury-_send]
#### [!toc] [#ShieldedTreasury-_send]
<APIItemCompact
  circuitSig='_send(
    recipient: Either<ZswapCoinPublicKey, ContractAddress>,
    color: Bytes<32>,
    amount: Uint<128>
  ) → ShieldedSendResult'
  kind="circuit"
  modulePrefix="ShieldedTreasury"
  stackParams="true"
>
  Sends shielded tokens from the treasury.

  Looks up the stored coin by color, verifies sufficient value,
  and executes the shielded send. `sendShielded` already routes any
  change back to this contract as a self-owned output. Unlike the
  stateless variant, this treasury RETAINS the change: it is recorded in
  the UTXO map for the next spend. The returned `result.change` therefore
  belongs to the treasury and must not be re-spent by the caller (doing
  so would double-spend the recorded coin).

  The returned `ShieldedSendResult` carries the sent and change coins
  in plaintext, so sinking it (returning it from an entry point, writing it
  to ledger, passing it cross-contract) discloses them. `_coins` publishes only
  the retained change coin, and nothing at all when the send leaves no change,
  so the sent coin's plaintext is disclosed beyond anything in public state.

  Access control is NOT enforced here.
  The consuming contract must gate this behind its own
  authorization policy.

  Requirements:

  - A coin of the given `color` must exist in the treasury.
  - The coin's value must be >= `amount`.
  - Send must not cause sent total overflow.
</APIItemCompact>

#### getReceivedMinusSent [toc] [#ShieldedTreasury-getReceivedMinusSent]
#### [!toc] [#ShieldedTreasury-getReceivedMinusSent]
<APIItemCompact
  circuitSig='getReceivedMinusSent(color: Bytes<32>) → Uint<128>'
  kind="circuit"
  modulePrefix="ShieldedTreasury"
>
  Returns the difference between cumulative received
  and cumulative sent totals for a color. Should equal
  `getTokenBalance` if accounting is consistent.

  The subtraction is unguarded. `_send` cannot drive the sent total
  past the received total. Change re-insertion never increments `_received`
  so the invariant holds for any consumer that goes through `_deposit` and
  `_send`. A consumer that writes the exported `_coins` directly can break
  it, and this circuit then fails as an unprovable range violation rather
  than a named assert.
</APIItemCompact>

#### _send [toc] [#ShieldedTreasuryStateless-_send]
#### [!toc] [#ShieldedTreasuryStateless-_send]
<APIItemCompact
  circuitSig='_send(
    coin: QualifiedShieldedCoinInfo,
    recipient: Either<ZswapCoinPublicKey, ContractAddress>,
    amount: Uint<128>
  ) → ShieldedSendResult'
  kind="circuit"
  modulePrefix="ShieldedTreasuryStateless"
  stackParams="true"
>
  Sends shielded tokens using a caller-provided coin.

  The coin is supplied by the caller rather than looked up from
  on-chain state; the token color is derived from `coin.color`.
  Executes the shielded send and returns the result untouched.
  `sendShielded` already routes any change back to this contract as a
  self-owned output, so `result.change` is a live, spendable coin. The
  implementing contract chooses what to do with it: retain it off-chain and
  pass it back as the `coin` for a later spend, or spend it onward to a
  different recipient in the same transaction via `sendImmediateShielded`.
  (Re-spending change is only meaningful when it goes somewhere other than
  self — `sendShielded` already routes it to self.) No balance or
  received/sent accounting is tracked on the ledger.

  <Callout type='warn'>
    The returned `ShieldedSendResult` holds the sent and change coins
    in plaintext (`nonce`, `color`, `value`). Consuming it in-circuit is safe
    (passing `result.change` to `sendImmediateShielded`, for instance). Returning
    it from your entry point, writing it to ledger, or passing it to another
    contract publishes those coin details, including the amount left over from
    the coin that was spent. Note the compiler will NOT stop you: the
    `disclose` calls below clear the witness taint, so such a return compiles
    with no `disclose` of your own and no marker at the disclosure site. If you
    do not need in-circuit change handling, ignore the result. The change is
    recoverable off-chain from the transaction's private proving state.
  </Callout>

  Access control is NOT enforced here.
  The consuming contract must gate this behind its own
  authorization policy.

  Requirements:

  - `coin.value` must be >= `amount`.
</APIItemCompact>

#### _drain [toc] [#ForwarderPrivate-_drain]
#### [!toc] [#ForwarderPrivate-_drain]
<APIItemCompact
  circuitSig='_drain(
    coin: QualifiedShieldedCoinInfo,
    parent: ZswapCoinPublicKey,
    opSecret: Bytes<32>,
    value: Uint<128>
  ) → ShieldedSendResult'
  kind="circuit"
  complexity="k=15, rows=23937"
  modulePrefix="ForwarderPrivate"
  stackParams="true"
>
  Spends a previously-deposited shielded coin to the parent,
  a coin public key. The caller proves knowledge of `(parent, opSecret)`
  matching the stored commitment; the coin is sent as a plain shielded note,
  so the parent stays hidden on-chain. If `coin.value` exceeds `value`,
  `sendShielded` routes the change back to this contract as a self-owned
  output; `_drain` returns it untouched via `result.change`. The
  implementing contract chooses what to do with it: leave it dwelling at
  the contract for a future drain, or spend it onward to a different
  recipient in the same transaction via `sendImmediateShielded`.

  The parent is a `ZswapCoinPublicKey`, never a `ContractAddress`: a shielded
  send to a contract publishes that contract's address in cleartext on the
  transaction (the protocol must route the coin to a named contract), which
  would defeat the private-parent guarantee. A coin public key is encrypted
  inside the Zswap output and never appears on the public transcript.

  Requirements:

  - Contract must be initialized.
  - `parent` must not be the zero key.
  - `_calculateParentCommitment(parent.bytes, opSecret) == _parentCommitment`.
  - `coin.value` must be >= `value` (enforced by `sendShielded`).

  <Callout type='warn'>
    **Losing the operational secret is permanent fund loss.** It
    is the sole drain authorization, with no rotation, revocation, or
    recovery path. If the operator misplaces it, every shielded coin
    accumulated at this contract is forever inaccessible, equivalent to
    losing a hot-wallet private key. Back it up offline before the first
    deposit and treat it with the same hygiene as a signing key.
  </Callout>
</APIItemCompact>

#### _calculateParentCommitment [toc] [#ForwarderPrivate-_calculateParentCommitment]
#### [!toc] [#ForwarderPrivate-_calculateParentCommitment]
<APIItemCompact
  circuitSig='_calculateParentCommitment(parentAddr: Bytes<32>, opSecret: Bytes<32>) → Bytes<32>'
  kind="pure"
  modulePrefix="ForwarderPrivate"
>
  Computes the parent commitment from `(parentAddr, opSecret)`.
  Pure circuit — used off-chain by the deployer to compute the
  constructor argument, and inside `_drain` for the preimage check.
  Callable without initialization.

  The first hash input is a fixed domain tag
  (`pad(32, "ForwarderPrivate:commitment")`). The tag prevents
  preimage collisions with other `persistentHash` users in the
  system that hash two `Bytes<32>` values — a colliding preimage
  crafted under a different domain cannot satisfy this commitment.
</APIItemCompact>
