#### _balances [toc] [#ConfidentialFungibleToken-_balances]
#### [!toc] [#ConfidentialFungibleToken-_balances]
<APIItemCompact
  circuitSig='_balances: Map<Bytes<32>, ElGamal_Ciphertext>'
  kind="ledger"
  id="ConfidentialFungibleToken-_balances"
>
  Dual-balance grief fix. `_balances` is the SPENDABLE (confirmed) balance that
  debits draw from; `_pending` is the incoming pool that credits land in. Only
  the owner moves pending -> spendable, via [sweep](#ConfidentialFungibleToken-sweep). So a third party spamming
  dust credits cannot churn a victim's spendable ciphertext and invalidate the
  victim's in-flight spend proofs (a liveness grief). A wallet's total balance
  is [balanceOf](#ConfidentialFungibleToken-balanceOf) (spendable) + [pendingOf](#ConfidentialFungibleToken-pendingOf) (pending).
</APIItemCompact>

#### _escrowSpendEpochs [toc] [#ConfidentialFungibleToken-_escrowSpendEpochs]
#### [!toc] [#ConfidentialFungibleToken-_escrowSpendEpochs]
<APIItemCompact
  circuitSig='_escrowSpendEpochs: Map<Bytes<32>, Map<Bytes<32>, Counter>>'
  kind="ledger"
  id="ConfidentialFungibleToken-_escrowSpendEpochs"
>
  Per-(owner, spender) escrow-spend counter, folded into the randomness
  `_spendEscrow` derives so repeat spends by one spender against one owner
  never share a one-time pad. It restarts for each pair, which is why both
  counterparties are bound in too; see `SpendRandomnessPreimage`.

  Kept out of `EscrowEntry`: [approve](#ConfidentialFungibleToken-approve) replaces that entry wholesale, so a
  counter living there would restart on every re-approve.

  Note that this exposes a per-pair spend count which is already derivable
  from tx history.
</APIItemCompact>

#### _creditEpochs [toc] [#ConfidentialFungibleToken-_creditEpochs]
#### [!toc] [#ConfidentialFungibleToken-_creditEpochs]
<APIItemCompact
  circuitSig='_creditEpochs: Map<Bytes<32>, Counter>'
  kind="ledger"
  id="ConfidentialFungibleToken-_creditEpochs"
>
  Per-account credit counter. `_credit` uses it as the nonce that keeps each
  credit's randomness distinct, so it MUST only ever increase. No circuit
  resets it. It is kept out of `_memos` for that reason: the memo list is
  prunable by its owner, and a nonce that could be walked back would let a
  reused seed repeat an earlier credit's randomness. The cost is that an
  account's lifetime credit count is now permanently readable from state.

  `Counter` is chosen for no-reset monotonicity, not commutativity. Its
  `increment` emits no pinned read, but `_credit` reads the value back to
  derive the nonce, and that read pins the recipient's key. Credits to one
  recipient still serialize; see the Concurrency note above.
</APIItemCompact>

#### wit_PlaintextBalance [toc] [#ConfidentialFungibleToken-wit_PlaintextBalance]
#### [!toc] [#ConfidentialFungibleToken-wit_PlaintextBalance]
<APIItemCompact
  circuitSig="wit_PlaintextBalance(ct: ElGamal_Ciphertext) → Uint<248>"
  kind="witness"
  id="ConfidentialFungibleToken-wit_PlaintextBalance"
>
  Returns the wallet's cached plaintext for the given
  ciphertext. Called whenever the circuit needs to verify a ciphertext's
  plaintext value (sender's main balance, escrow ciphertext during spend,
  prior escrow during refund, etc.).

  The ciphertext is passed explicitly so the wallet can route to the right
  cached plaintext by ciphertext identity. This avoids call-order
  conventions (which would be brittle to circuit refactors) and lets the
  wallet maintain a `Map<ElGamal_Ciphertext, Uint248>` lookup.

  Verified in-circuit by `ElGamal_assertDecryptsTo`: a wrong plaintext
  fails the assertion `Dec(ct, EK) == claimedValue`.
</APIItemCompact>

#### wit_RandomnessSeed [toc] [#ConfidentialFungibleToken-wit_RandomnessSeed]
#### [!toc] [#ConfidentialFungibleToken-wit_RandomnessSeed]
<APIItemCompact
  circuitSig="wit_RandomnessSeed() → Bytes<32>"
  kind="witness"
  id="ConfidentialFungibleToken-wit_RandomnessSeed"
>
  Returns a single 32-byte seed from which all per-operation
  randomness (and each memo's ephemeral) is derived in-circuit.

  Seed freshness is load-bearing for confidentiality on EVERY path (see the
  module header). The derivation is deterministic and public, so an observer
  who knows the seed can strip a memo's mask and read the delivered amount, and
  recover balance/escrow amounts from the public ciphertexts. Seed REUSE leaks
  plaintext differences and the circuit does NOT prevent it on most paths.
  `_spendEscrow` is an exception (its randomness folds the spend epoch and both
  counterparties); the credit path folds the recipient's `_creditEpochs`
  counter as defense in depth, and that covers credits alone. The seed MUST be
  fresh, high-entropy, and secret for every invocation.
</APIItemCompact>

#### MAX_TRANSFER_VALUE [toc] [#ConfidentialFungibleToken-MAX_TRANSFER_VALUE]
#### [!toc] [#ConfidentialFungibleToken-MAX_TRANSFER_VALUE]
<APIItemCompact
  circuitSig="MAX_TRANSFER_VALUE() → Uint<128>"
  kind="pure"
  modulePrefix="ConfidentialFungibleToken"
>
  Maximum allowed value per single transfer / mint / burn /
  approve: the `Uint<128>` maximum. The prior `2^48` cap existed only to keep
  wallet-side discrete-log recovery tractable; with the ECDH memo delivering
  values directly (see `crypto/EcdhMask`), that constraint is gone. Values stay
  well under the Jubjub scalar-field order, so homomorphic sums do not wrap.

  <Callout type='info'>
    This equals the argument type's own maximum, so the per-op check is
    redundant today. KEEP IT: it compares against a hard constant rather than
    the argument type, so it still catches a later widening of the transfer
    type — which is what the balance-claim width is sized against.
  </Callout>
</APIItemCompact>

#### allowance [toc] [#ConfidentialFungibleToken-allowance]
#### [!toc] [#ConfidentialFungibleToken-allowance]
<APIItemCompact
  circuitSig="allowance(owner: Bytes<32>, spender: Bytes<32>) → EscrowEntry"
  kind="circuit"
  complexity="k=10, rows=938"
  modulePrefix="ConfidentialFungibleToken"
>
  Returns the escrow entry (the encrypted allowance) that `owner`
  granted `spender`. When no allowance exists, returns a well-formed
  encrypted-zero entry (its encrypted amounts decrypt to 0, analogous to an
  ERC-20 zero allowance) rather than `default<EscrowEntry>`: the returned
  Jubjub points are on-curve, so the view is safe to prove (e.g. through a
  contract-to-contract call) and safe for a wallet to decrypt, whereas a zeroed
  default holds off-curve points. The cap is encrypted, not public.

  <Callout type='info'>
    "No allowance" and "an allowance of 0" both read as encrypted-zero;
    a caller that must distinguish them reads `_escrow` membership off-chain. This
    getter grants nothing, the spend path ([transferFrom](#ConfidentialFungibleToken-transferFrom)/`burnFrom`) gates on
    `_escrow` membership independently, so a non-existent allowance is unspendable.
  </Callout>
</APIItemCompact>

#### _move [toc] [#ConfidentialFungibleToken-_move]
#### [!toc] [#ConfidentialFungibleToken-_move]
<APIItemCompact
  circuitSig="_move(to: Bytes<32>, value: Uint<128>) → Bytes<32>"
  kind="circuit"
  complexity="k=16, rows=43690"
  modulePrefix="ConfidentialFungibleToken"
>
  The conserving value-movement primitive: debits the caller and
  credits `to` by the same `value`, net zero. It NEVER changes supply, so it is
  the safe surface for composition and the primitive this supply-free base
  exposes. [transfer](#ConfidentialFungibleToken-transfer) is [_move](#ConfidentialFungibleToken-_move) plus a self-transfer guard; supply-changing
  operations (`mint`/`burn`) live in a separate layer outside this conserving
  surface, and only they may break conservation.

  <Callout type='info'>
    Like [transfer](#ConfidentialFungibleToken-transfer), the credit lands in the recipient's pending pool
    (see the dual-balance note); the caller sweeps their own incoming value.
  </Callout>

  Self-move (`to` == caller) is PERMITTED here, unlike [transfer](#ConfidentialFungibleToken-transfer), which
  rejects it. A self-move is conserving and safe: it debits the caller's
  spendable and credits the caller's own pending (net zero, distinct ledger
  cells; the value is recovered with [sweep](#ConfidentialFungibleToken-sweep)). [transfer](#ConfidentialFungibleToken-transfer)'s self-transfer guard
  is therefore a UX choice, not a safety requirement: it spares users a
  self-transfer with no foreseeable benefit (a shuffle of spendable into
  pending plus a self-memo). This primitive stays permissive so a composer can
  set its own policy; add a `to != caller` check in the wrapper to reject a
  self-move.

  Requirements:

  - Contract is initialized.
  - The caller is registered with a spendable balance of at least `value`.
  - `to` is registered.
</APIItemCompact>

#### sweep [toc] [#ConfidentialFungibleToken-sweep]
#### [!toc] [#ConfidentialFungibleToken-sweep]
<APIItemCompact
  circuitSig="sweep() → Bytes<32>"
  kind="circuit"
  complexity="k=13, rows=7585"
  modulePrefix="ConfidentialFungibleToken"
>
  Sweeps the caller's incoming `pending` pool into their
  `spendable` balance. Credits land in `pending` (see the dual-balance note);
  this [sweep](#ConfidentialFungibleToken-sweep) is the ONLY path from pending into spendable, and only the owner
  can invoke it (the caller proves BOTH witness secrets: the account secret
  identifies the account, the encryption secret proves the caller can read it).
  So a third party spamming credits cannot force a victim's spendable ciphertext
  to change, which is what would otherwise invalidate the victim's in-flight
  spend proofs (a liveness grief).

  <Callout type='info'>
    Purely homomorphic: adds the two ciphertexts (same key) and resets
    pending to Enc(0). No plaintext is needed; the wallet already learned the
    pending amounts from its memos.
  </Callout>

  Requirements:

  - Contract is initialized.
  - The caller is registered.
  - The caller holds the encryption secret registered for their account.
</APIItemCompact>

#### approve [toc] [#ConfidentialFungibleToken-approve]
#### [!toc] [#ConfidentialFungibleToken-approve]
<APIItemCompact
  circuitSig="approve(spender: Bytes<32>, value: Uint<128>) → Bytes<32>"
  kind="circuit"
  complexity="k=16, rows=45114"
  modulePrefix="ConfidentialFungibleToken"
>
  Sets `spender`'s allowance over the caller's balance to `value`
  via an escrow: the caller's main balance is debited by `value`, and matching
  encryptions are stored for the spender and the owner. Re-approving first
  refunds any prior escrow, so allowances replace rather than stack. The cap
  is not public.

  <Callout type='info'>
    Returns the caller's (approver's) `accountId` for caller-side gating.
  </Callout>

  Also stores an owner-readable `ownerMemo` (ECDH one-time pad; see
  `crypto/EcdhMask`) in the escrow entry, carrying the current remaining
  allowance (= `value` here, refreshed to the reduced remaining on every
  spend). This is what lets the owner prove the post-refund balance on a later
  re-approve or revoke after a partial spend; without it a partial spend would
  strand the escrow. See the `EscrowEntry` field doc.

  Requirements:

  - Contract is initialized.
  - `value` is within [MAX_TRANSFER_VALUE](#ConfidentialFungibleToken-MAX_TRANSFER_VALUE).
  - `spender` is registered, is not the zero account, and is not the caller.
  - The caller is registered with a balance of at least `value`.
</APIItemCompact>

#### clearMemos [toc] [#ConfidentialFungibleToken-clearMemos]
#### [!toc] [#ConfidentialFungibleToken-clearMemos]
<APIItemCompact
  circuitSig="clearMemos(expectedEpoch: Uint<64>) → []"
  kind="circuit"
  complexity="k=13, rows=7053"
  modulePrefix="ConfidentialFungibleToken"
>
  Clears the caller's memo list, letting a wallet that has folded
  its memos into its local balance cache prune on-chain memo storage.

  `expectedEpoch` is the caller's view of its `_creditEpochs` value at the
  moment it read the list. The call is rejected unless that still matches, so
  a credit landing between the read and this transaction is never silently
  discarded. The wallet retries against the memos it has now seen. A wallet
  therefore reads its memo list and its epoch together, folds the memos into
  its cache, and passes that epoch back here.

  <Callout type='warn'>
    Clearing memos is destructive and can permanently lock funds. The
    on-chain balance ciphertext is not directly decryptable (discrete-log
    bound), so a wallet reconstructs its balance by replaying memos. Clearing
    them without a durable off-chain record of the balance loses the ability to
    recover it; and because spending requires proving the balance plaintext, the
    funds become unspendable, not merely undisplayable. Clear only memos already
    folded into a durable cache/backup. The epoch check only rules out a credit
    the caller has not seen; it does not make clearing safe for memos the caller
    never folded in.
  </Callout>

  Requirements:

  - Contract is initialized.
  - The caller is registered.
  - The caller holds the encryption secret registered for their account.
  - The caller has a memo list.
  - `expectedEpoch` equals the caller's current credit epoch.
</APIItemCompact>

## ConfidentialFungibleTokenPublicSupply [toc] [#ConfidentialFungibleTokenPublicSupply]
<APIGithubLinkHeader
    moduleName="ConfidentialFungibleTokenPublicSupply"
    link={`https://github.com/OpenZeppelin/compact-contracts/blob/v0.3.0/contracts/src/token/extensions/ConfidentialFungibleTokenPublicSupply.compact`}
/>

```ts
import "./node_modules/@openzeppelin/compact-contracts/token/extensions/ConfidentialFungibleTokenPublicSupply";
```

Optional standalone extension that adds public supply accounting to a ConfidentialFungibleToken. It imports no token
module and needs no initialization. "Public" supply means the total, and therefore each mint and burn amount, is
disclosed on chain through the delta; balances stay confidential. The composing contract pairs each accounting block
with the matching token operation.
