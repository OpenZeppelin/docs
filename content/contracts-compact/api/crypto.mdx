This page provides the full API for the Crypto modules.

<Callout type='info'>
  For an overview of the modules, read the [Crypto guide](../crypto).
</Callout>

The page covers the following modules:

- [ElGamal](#ElGamal): exponential ElGamal encryption over Jubjub with homomorphic addition and re-randomization.
- [EcdhMask](#EcdhMask): an ECDH-derived mask for encrypting a value to a recipient's public key.

#### secretToScalar [toc] [#ElGamal-secretToScalar]
#### [!toc] [#ElGamal-secretToScalar]
<APIItemCompact
  circuitSig='secretToScalar(secret: Bytes<32>) → Field'
  kind="pure"
  modulePrefix="ElGamal"
>
  Maps a 32-byte secret to a valid Jubjub scalar. See the
  module-level hash-to-scalar note for why `degradeToTransient` is required.

  Domain separation here is load-bearing, not cosmetic. This output is
  the private key protecting every ciphertext held under an account. Public
  account identifiers derived from `Utils.computeAccountId`, for example,
  are computed as `persistentHash([secretKey])`, and that identifier
  is stored in the clear as a ledger map key. Untagged, this circuit
  would compute that same hash, so a secret used in both roles would
  have its encryption key recoverable from a published identifier by applying
  `degradeToTransient`. The tag makes the two derivations unrelated, so a
  wallet MAY safely derive its account secret and its encryption secret from
  common key material.

  The tag is FIRST, deliberately. [expandRandomness](#ElGamal-expandRandomness) hashes
  `[seed, tag]` with both slots caller-supplied, so tagging this circuit as
  `[secret, tag]` would make `secretToScalar(x)` identical to
  `expandRandomness(x, <this tag>)` reachable by passing this domain string
  to the parameter that exists to receive domain strings. Leading with the
  tag means reproducing this output through [expandRandomness](#ElGamal-expandRandomness) would require
  passing the domain constant as the *seed*. Do not normalise the orderings.
</APIItemCompact>

  kind="pure"
  modulePrefix="ElGamal"
>
  The identity ciphertext `Enc(0)` (both components are the
  curve identity). Useful for initializing a fresh balance.

  <Callout type='info'>
    This is a fixed, deterministic value `(O, O)` — NOT a hiding
    encryption. It is publicly recognizable, so a slot left at [encryptZero](#ElGamal-encryptZero) is
    distinguishable as never-written. Rerandomize (or credit with fresh `r`)
    before treating it as private.
  </Callout>

#### encryptPoint [toc] [#ElGamal-encryptPoint]
#### [!toc] [#ElGamal-encryptPoint]
<APIItemCompact
  circuitSig='encryptPoint(
    pk: JubjubPoint,
    m: JubjubPoint,
    r: Field
  ) → Ciphertext'
  kind="pure"
  modulePrefix="ElGamal"
  stackParams="true"
>
  Encrypts an arbitrary message point `m` under `pk` with
  randomness `r`, producing the ciphertext `(g^r, pk^r * m)`. This is the
  general (non-lifted) ElGamal encryption; [encrypt](#ElGamal-encrypt) is the lifted special
  case `encryptPoint(pk, g^value, r)`.

  <Callout type='info'>
    `m` (like `pk`) is constrained into the prime-order subgroup by the
    runtime (see the module-level subgroup note), so no in-circuit membership
    check is performed. `pk` is asserted non-identity and `r` non-zero — the
    two inputs that would zero the mask and expose `m` (see the weak-keys and
    randomness notes). Decrypting `m` is only feasible when it is a known or
    small-exponent point; the caller owns that concern (the lifted [encrypt](#ElGamal-encrypt)
    bounds it via the discrete-log range).
  </Callout>

  Requirements:

  - `pk` is not the identity point.
  - `r` is non-zero.
</APIItemCompact>

#### encrypt [toc] [#ElGamal-encrypt]
#### [!toc] [#ElGamal-encrypt]

  modulePrefix="ElGamal"

  Produces a fresh ciphertext of `value` under `pk` with

  as a `Field` directly to avoid a redundant `Bytes<32> -> Field` conversion

  Requirements:

  - `pk` is not the identity point.
  - `r` is non-zero.
</APIItemCompact>

#### add [toc] [#ElGamal-add]
#### [!toc] [#ElGamal-add]
<APIItemCompact
  circuitSig='add(a: Ciphertext, b: Ciphertext) → Ciphertext'
  kind="pure"
  modulePrefix="ElGamal"
>
  Homomorphically adds two ciphertexts: `Enc(a) + Enc(b)`
  decrypts to `a + b`. This is the defining additive-homomorphism primitive
  and combines two independently produced ciphertexts componentwise.

  <Callout type='info'>
    Both inputs MUST be encrypted under the same public key for the
    result to decrypt under that key's secret; combining ciphertexts under
    different keys yields a ciphertext no single key can open. The randomness
    of the result is the sum of the inputs' randomness, so the result is a
    valid fresh ciphertext under that key.
  </Callout>
</APIItemCompact>

#### sub [toc] [#ElGamal-sub]
#### [!toc] [#ElGamal-sub]
<APIItemCompact
  circuitSig='sub(a: Ciphertext, b: Ciphertext) → Ciphertext'
  kind="pure"
  modulePrefix="ElGamal"
>
  Homomorphically subtracts two ciphertexts: `Enc(a) - Enc(b)`
  decrypts to `a - b`. Implemented as `add(a, negate(b))`.

  <Callout type='info'>
    Same-key requirement as [add](#ElGamal-add). The caller MUST ensure the
    underlying plaintext subtraction does not underflow; this circuit cannot
    check it (see [subEncrypted](#ElGamal-subEncrypted)).
  </Callout>
</APIItemCompact>

#### scalarMul [toc] [#ElGamal-scalarMul]
#### [!toc] [#ElGamal-scalarMul]
<APIItemCompact
  circuitSig='scalarMul(ct: Ciphertext, k: Field) → Ciphertext'
  kind="pure"
  modulePrefix="ElGamal"
>
  Homomorphically multiplies the plaintext of `ct` by a public
  scalar `k`: if `ct` encrypts `v` then the result encrypts `k * v` under the
  same key. Both components are scaled by `k`, so the randomness scales to
  `k * r` and the result is a valid fresh ciphertext under that key.

  This is the scalar-multiplication leg of the homomorphism, and the only way
  to express linear combinations: a weighted sum `Enc(3a + 5b)` is
  `add(scalarMul(ca, 3), scalarMul(cb, 5))`, which repeated [add](#ElGamal-add) cannot do
  for large weights.

  <Callout type='info'>
    `k` MUST be a valid Jubjub scalar (less than the subgroup order);
    larger values fault `ecMul` (see the module-level hash-to-scalar note). The
    caller also remains responsible for the discrete-log bound — `k * v` must
    stay within the range a recovery search can clear.
  </Callout>
</APIItemCompact>

#### rerandomize [toc] [#ElGamal-rerandomize]
#### [!toc] [#ElGamal-rerandomize]
<APIItemCompact
  circuitSig='rerandomize(
    ct: Ciphertext,
    pk: JubjubPoint,
    r: Field
  ) → Ciphertext'
  kind="pure"
  modulePrefix="ElGamal"
  stackParams="true"
>
  Rerandomizes `ct`: returns a fresh ciphertext of the same
  plaintext under the same key `pk`, using new randomness `r`. The output is
  unlinkable to the input (it is a uniformly fresh encryption of the same
  value) yet decrypts identically. Equivalent to homomorphically adding an
  encryption of zero.

  <Callout type='info'>
    `r = 0` is rejected (it would be a no-op via the [encryptPoint](#ElGamal-encryptPoint)
    zero-randomness assert). One silent failure mode remains that the circuit
    cannot catch: a `pk` that is not the key `ct` was encrypted under corrupts
    the plaintext (the result no longer decrypts to the original value). Pass
    fresh randomness and the matching `pk`.
  </Callout>

  Requirements:

  - `pk` is not the identity point.
  - `r` is non-zero.
</APIItemCompact>

#### assertDecryptsTo [toc] [#ElGamal-assertDecryptsTo]
#### [!toc] [#ElGamal-assertDecryptsTo]
<APIItemCompact
  circuitSig='assertDecryptsTo(
    ct: Ciphertext,
    pk: JubjubPoint,
    ek: Bytes<32>,
    claimedValue: Uint<248>
  ) → []'
  kind="pure"
  modulePrefix="ElGamal"
  stackParams="true"
>
  Asserts that `ct` decrypts under `(pk, ek)` to `claimedValue`,
  and that `ek` is the secret for `pk`. This is the in-circuit verification
  path an importing module uses to bind its witness-supplied `ek` and cached
  plaintext to publicly stored state: a wrong `ek` fails the key check, a
  wrong plaintext fails the decryption check. Lifted special case of
  [assertDecryptsToPoint](#ElGamal-assertDecryptsToPoint) with the message point `g^claimedValue`.

  <Callout type='info'>
    `claimedValue` is the widest `Uint` Compact offers, so this parameter
    never bounds a caller. A narrower value costs proportionally fewer rows: the
    range constraint belongs to where the value is declared, not to this
    signature.
  </Callout>

  <Callout type='warn'>
    The claim domain must stay below the Jubjub subgroup order `l`:
    verification compares `g^claimedValue`, so two claims congruent mod `l` are
    indistinguishable. `Uint<248>` clears `l` (~2^251.86) by under 4 bits, and
    that width is set by Compact's cap rather than by this bound. 251 is the
    widest sound `Uint` if the cap ever rises.
  </Callout>

  Requirements:

  - `ek` is the secret for `pk`.
  - `ct` decrypts under `(pk, ek)` to `claimedValue`.
</APIItemCompact>

#### kdf [toc] [#EcdhMask-kdf]
#### [!toc] [#EcdhMask-kdf]
<APIItemCompact
  circuitSig='kdf(sShared: JubjubPoint, domain: Bytes<32>) → Field'
  kind="pure"
  modulePrefix="EcdhMask"
>
  Derives the field mask from the ECDH shared secret point,
  domain-separated by a caller-supplied `domain` tag. Hashes the point to
  `Bytes<32>`, then re-hashes it with the domain tag and truncates into the
  field via `degradeToTransient`. The consumer chooses `domain` (so this
  module is not tied to any one protocol) and MUST use the same value on
  encrypt and decrypt.

  Uses `persistentHash` deliberately: the recipient reproduces this mask
  to decrypt, possibly across a platform upgrade, so it must be upgrade-stable.
</APIItemCompact>
