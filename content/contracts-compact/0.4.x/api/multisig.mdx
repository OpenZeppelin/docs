title: Multisig API
---

This page provides the full API for the Multisig modules.

<Callout type='info'>
  For an overview of the modules, read the [Multisig guide](../multisig).
</Callout>

The page covers the following modules:

- [Signer](#Signer): the registry of who may approve and how many approvals are required, generic over the signer identity type.
- [Secp256k1EcdsaMultisig](#Secp256k1EcdsaMultisig): a `t`-of-`n` signer set of secp256k1 key commitments that verifies `t` ECDSA approvals over a digest.
- [ProposalManager](#ProposalManager): the lifecycle of transfer proposals, independent of the token kind.
- [ShieldedTreasury](#ShieldedTreasury): holds one shielded coin per token color on the ledger and sends from it.
- [ShieldedTreasuryStateless](#ShieldedTreasuryStateless): receives and sends shielded coins without keeping any ledger state.
- [UnshieldedTreasury](#UnshieldedTreasury): holds unshielded tokens with a tracked per-color balance.
- [ForwarderPrivate](#ForwarderPrivate): forwards shielded deposits to a parent stored as a commitment.
- [ForwarderShielded](#ForwarderShielded): forwards shielded deposits to a public parent in the same transaction.
- [ForwarderUnshielded](#ForwarderUnshielded): forwards unshielded deposits to a public parent in the same transaction.
- [ShieldedMultiSigV2](#ShieldedMultiSigV2): preset; a stateless shielded wallet whose spends are authorized by `t` EIP-712 ECDSA signatures.
- [NativeShieldedTokenIssuer](#NativeShieldedTokenIssuer): preset; a native shielded token minted and burned only with `t` EIP-712 ECDSA signatures.

## Signer [toc] [#Signer]
<APIGithubLinkHeader
    moduleName="Signer"
    link={`https://github.com/OpenZeppelin/compact-contracts/blob/v0.4.0/contracts/src/multisig/Signer.compact`}
/>

```ts
import "./node_modules/@openzeppelin/compact-contracts/multisig/Signer"<Bytes<32>>;
```

`Signer<T>` is generic over the signer identity type `T`, chosen at import time (for example `Bytes<32>`, `JubjubPoint`, or `Either<ZswapCoinPublicKey, ContractAddress>`).
The module never resolves the caller; the consuming contract passes an identity in.
It has no `initialize`: the consuming contract registers signers with [_addSigner](#Signer-_addSigner) and sets the threshold with [_changeThreshold](#Signer-_changeThreshold) or [_setThreshold](#Signer-_setThreshold).

#### assertThresholdMet [toc] [#Signer-assertThresholdMet]
#### [!toc] [#Signer-assertThresholdMet]
<APIItemCompact
  circuitSig='assertThresholdMet(approvalCount: Uint<8>) → []'
  kind="circuit"
  complexity="k=9, rows=52"
  modulePrefix="Signer"
>
  Asserts that the given approval count meets the threshold.

  <Callout type='info'>
    `approvalCount` is supplied by the consuming contract and is
    compared against the threshold only. This circuit never consults the signer
    registry. Ensuring the count reflects distinct, currently-registered signers
    is the consuming contract's responsibility, and a contract whose approval
    accounting is not itself gated by [assertSigner](#Signer-assertSigner) gets no protection here.

    The count is deliberately left unbounded by `_signerCount`: approvals
    collected before a signer was removed must still count toward a threshold
    the remaining signers satisfy, and bounding the count would reject those.
    See the stale-signer-set guidance in the module header.
  </Callout>

  Requirements:

  * Ledger threshold must be set (not be zero). An unconfigured module has a
    zero threshold, so this rejects before any approval count is compared.
  * `approvalCount` must be >= threshold.
</APIItemCompact>

#### _setThreshold [toc] [#Signer-_setThreshold]
#### [!toc] [#Signer-_setThreshold]
<APIItemCompact
  circuitSig='_setThreshold(newThreshold: Uint<8>) → []'
  kind="circuit"
  complexity="k=6, rows=38"
  modulePrefix="Signer"
>
  Sets the approval threshold without checking
  against the current signer count.

  <Callout type='warn'>
    This is intended for use during contract construction
    or custom setup flows where signers may not yet be registered.

    Leaving `newThreshold` above the signer count is permitted and expected
    mid-setup, and is not self-enforcing: [assertThresholdMet](#Signer-assertThresholdMet) compares
    `approvalCount` against the threshold alone, so a caller supplying a matching
    count satisfies it even against an empty registry. Contracts must not gate
    operations on [assertThresholdMet](#Signer-assertThresholdMet) while setup is incomplete. Lower the
    threshold with [_setThreshold](#Signer-_setThreshold); [_changeThreshold](#Signer-_changeThreshold) cannot lower one while the
    signer count is zero, because that would require a zero threshold.
  </Callout>

  <Callout type='info'>
    Access control is NOT enforced here.
    The consuming contract must gate this behind its own
    authorization policy. Use [_changeThreshold](#Signer-_changeThreshold) for
    operational threshold changes with signer count validation.
  </Callout>

  Requirements:

  * `newThreshold` must not be zero.
</APIItemCompact>

`Secp256k1EcdsaMultisig<#t>` takes the threshold `t` as its import generic; `initialize` fixes the signer count `n`.
It wraps a `Signer<Bytes<32>>` registry, requires ZKIR v3, and must be imported at one width per contract and never alongside `Signer`.

#### initialize [toc] [#Secp256k1EcdsaMultisig-initialize]

#### assertApprovals [toc] [#Secp256k1EcdsaMultisig-assertApprovals]
#### [!toc] [#Secp256k1EcdsaMultisig-assertApprovals]
<APIItemCompact
  circuitSig='assertApprovals(
    msgHash: Bytes<32>,
    pubkeys: Vector<t, Secp256k1Point>,
    signatures: Vector<t, Secp256k1EcdsaSignature>
  ) → []'
  kind="circuit"
  modulePrefix="Secp256k1EcdsaMultisig"
  stackParams="true"
>
  Verifies `t` approvals over `msgHash`: distinct registered signers,
  each with a valid low-s signature.
  `pubkeys` and `signatures` are parallel: entry `i` of each belongs to the same signer.

  The threshold check runs first, so an uninitialized registry fails before any signature work.
  Then all `t(t-1)/2` pairs of commitments are compared, and each entry's commitment and signature are checked.
  Verification goes through [secp256k1EcdsaVerifyLowS](./crypto#Ecdsa), so a high-s encoding is an invalid signature.
  The commitments of the `t` approvers are disclosed, so which signers approved is public; keys and signatures are not.

  Cost (ZKIR v3): `t = 1` is k=16, rows=40538; `t = 2` is k=17, rows=64908; `t = 3` is k=17, rows=94995.

  <Callout type='info'>
    This circuit verifies signatures over whatever `msgHash` it is handed.
    Replay, domain, and instance binding belong in the consumer's digest.
  </Callout>

  Requirements:

  * The module must be initialized.
  * No two entries may be the same signer.
  * Every public key must hash to a registered signer commitment.
  * Every signature must be valid over `msgHash` and use the low-s encoding.
</APIItemCompact>

>

  </Callout>

  Requirements:

</APIItemCompact>

#### ProposalStatus [toc] [#ProposalManager-ProposalStatus]
#### [!toc] [#ProposalManager-ProposalStatus]
<APIItemCompact
  circuitSig="enum ProposalStatus { Inactive, Active, Executed, Cancelled, Expired }"
  kind="enum"
  id="ProposalManager-ProposalStatus"
>
  Proposal lifecycle states. `Proposal.status` stores `Active`, `Executed`, or `Cancelled`;
  [getProposalStatus](#ProposalManager-getProposalStatus) derives the other two.

  * `Inactive`: no proposal with that id exists. Never stored.
  * `Active`: created and not retired. Executable only while the block time is below `Proposal.expiry`.
  * `Executed`: [_markExecuted](#ProposalManager-_markExecuted) ran. Terminal.
  * `Cancelled`: [_cancelProposal](#ProposalManager-_cancelProposal) ran. Terminal.
  * `Expired`: stored `Active` with an `expiry` at or before the current block time. Never stored.
</APIItemCompact>

#### Proposal [toc] [#ProposalManager-Proposal]
#### [!toc] [#ProposalManager-Proposal]
<APIItemCompact
  circuitSig="struct Proposal { to: Recipient, color: Bytes<32>, amount: Uint<128>, expiry: Uint<64>, status: ProposalStatus }"
  kind="struct"
  id="ProposalManager-Proposal"
>
  A transfer proposal: recipient, token color, amount, deadline, and stored lifecycle stage.
  `expiry` is in seconds since the Unix epoch. Reaching a terminal stage changes `status` only,
  so an executed or cancelled proposal keeps the deadline it was created with.

  <Callout type='warn'>
    `expiry` marks when a proposal STOPS being executable, not when it starts:
    an `Active` proposal is executable while `blockTime < expiry` and inert once `blockTime >= expiry`.
    The module implements no execution delay; a consumer that needs one must compose it.
  </Callout>
</APIItemCompact>

#### _createProposal [toc] [#ProposalManager-_createProposal]
#### [!toc] [#ProposalManager-_createProposal]
<APIItemCompact
  circuitSig='_createProposal(
    to: Recipient,
    color: Bytes<32>,
    amount: Uint<128>,
    expiry: Uint<64>
  ) → Uint<64>'
  kind="circuit"
  complexity="k=10, rows=883"
  modulePrefix="ProposalManager"
  stackParams="true"
>
  Creates a new proposal that is executable until `expiry`,
  in seconds since the Unix epoch.

  <Callout type='warn'>
    The recipient is NOT validated beyond being well-typed. Two
    consequences the consumer must handle:

    * A `kind` the execution rail cannot accept (an `UnshieldedUser` recipient
    on a shielded treasury, say) creates a proposal that passes here and then
    reverts in [toShieldedRecipient](#ProposalManager-toShieldedRecipient) at execution. It stays `Active` and
    unexecutable on that rail until [_cancelProposal](#ProposalManager-_cancelProposal) retires it or its
    `expiry` lapses.
    * A zero or otherwise unspendable `address` is accepted, and funds sent to
    it on execution are unrecoverable.
  </Callout>

  <Callout type='info'>
    `_nextProposalId` is incremented and then read back for the map key,
    making this a pinned read-modify-write.

  circuitSig='_drain(
    coin: QualifiedShieldedCoinInfo,
    parent: ZswapCoinPublicKey,
    opSecret: Bytes<32>,
    value: Uint<128>
  ) → ShieldedSendResult'
  kind="circuit"
  complexity="k=15, rows=23837"
  modulePrefix="ForwarderPrivate"
  stackParams="true"
>
  Spends a previously-deposited shielded coin to the parent,
  a coin public key. The caller proves knowledge of `(parent, opSecret)`
  matching the stored commitment; the coin is sent as a plain shielded note,
  so the parent stays hidden from anyone who holds no deposited coin.
  If `coin.value` exceeds `value`,
  `sendShielded` routes the change back to this contract as a self-owned
  output; [_drain](#ForwarderPrivate-_drain) returns it untouched via `result.change`. The
  implementing contract chooses what to do with it: leave it dwelling at
  the contract for a future drain, or spend it onward to a different
  recipient in the same transaction via `sendImmediateShielded`.

  The parent is a `ZswapCoinPublicKey`, never a `ContractAddress`: a shielded
  send to a contract publishes that contract's address in cleartext on the
  transaction (the protocol must route the coin to a named contract), which
  would defeat the private-parent guarantee. A coin public key is encrypted
  inside the Zswap output and never appears on the public transcript.

  Requirements:

  * Contract must be initialized.
  * `parent` must not be the zero key.
  * `_calculateParentCommitment(parent.bytes, opSecret) == _parentCommitment`.
  * `coin.value` must be >= `value` (enforced by `sendShielded`).

  <Callout type='warn'>
    **Losing the operational secret is permanent fund loss.** It
    is the sole drain authorization, with no rotation, revocation, or
    recovery path. If the operator misplaces it, every shielded coin
    accumulated at this contract is forever inaccessible, equivalent to
    losing a hot-wallet private key. Back it up offline before the first
    deposit and treat it with the same hygiene as a signing key.
  </Callout>
</APIItemCompact>

  receives it and burns it in the same call. Any change goes to `refundTo`.
  Returns the refund coin, or `none` if the coin was burned in full.

  <Callout type='info'>
    The returned refund coin info is the only copy available to
    `refundTo`; deliver it out of band.
  </Callout>

  <Callout type='warn'>
    `amount`, `coin.value`, and `refundTo` stay hidden only while `coin` carries a nonce the observer does not know.
    A coin passed straight from [mint](#NativeShieldedTokenIssuer-mint) has a derived nonce,
    so the burn links to its mint and all three are recoverable by trial.
    For an unlinkable burn the holder re-nonces the coin first with a wallet self-transfer; the contract cannot enforce this.
  </Callout>

  Requirements:

  * No two entries may be the same signer.
  * Every public key must hash to a registered signer commitment.
  * Every signature must be valid over the burn message hash and use the low-s encoding.
  * `coin.color` is this contract's token color.
  * `amount` is less than or equal to `coin.value`.
  * `refundTo` is not zero.
</APIItemCompact>

#### burnFromSelf [toc] [#NativeShieldedTokenIssuer-burnFromSelf]

    signatures: Vector<t, Secp256k1EcdsaSignature>
  ) → Maybe<ShieldedCoinInfo>'
  kind="circuit"
  complexity="k=17, rows=104973"
  modulePrefix="NativeShieldedTokenIssuer"
  stackParams="true"
>
  Burns `amount` from a coin this contract holds, authorized
  by threshold signatures over
  `BurnFromSelf(bytes32 contractAddress,uint256 nonce,uint256 amount,bytes32 coinNonce,uint256 coinValue)`.

  The operator supplies the `QualifiedShieldedCoinInfo` from the off-chain
  UTXO pool. On a partial burn the change is auto-received by the contract
  and returned; it replaces `coin` as the contract's holding, so the
  operator must persist it.
  The digest binds `coin.nonce` and `coin.value`, so approvals authorize one
  specific holding rather than an amount. Pick the coin before collecting signatures.

  Requirements:

  * No two entries may be the same signer.
  * Every public key must hash to a registered signer commitment.
  * Every signature must be valid over the burn-from-self message hash and use the low-s encoding.
  * `coin.color` is this contract's token color.
  * `amount` is less than or equal to `coin.value`.
  * `coin.nonce` and `coin.value` match the approved coin.
</APIItemCompact>
